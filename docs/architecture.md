# Architecture

## Request Flow

FastAPI receives HTTP requests and routes them through modules in `app/api`.

Typical state-changing request flow:

1. Request enters a route handler.
2. Authentication dependency resolves the current user when required.
3. The route loads or validates resource existence.
4. Business logic runs in a service module under `app/services`.
5. SQLAlchemy persists changes through a request-scoped session.
6. Audit logging records safe metadata for important state changes.
7. Pydantic schemas serialize the response.

Routes should stay thin. Service modules own database and domain operations.

## Async Triage Flow

`POST /api/incidents/{incident_id}/triage-jobs` creates a `TriageJob` and enqueues a Celery task. The HTTP request returns `202 Accepted` after dispatching the task; it does not wait for triage completion.

Worker flow:

1. Celery receives `process_triage_job(job_id)`.
2. The worker opens its own SQLAlchemy session.
3. The job is marked `running`.
4. The incident is loaded.
5. Existing triage generation service creates a `TriageResult`.
6. The job is marked `succeeded` and linked to the triage result.
7. On failure, the job is marked `failed` and `error_message` is stored.
8. The worker closes its DB session in `finally`.

Redis is the Celery broker and result backend.

## LangGraph Workflow

The triage graph lives in `app/ai/triage_graph.py`.

Nodes:

1. `normalize_incident`
2. `classify_severity`
3. `retrieve_runbooks`
4. `generate_recommendations`
5. `validate_output`

Graph nodes return state updates. They do not write directly to the database. Persistence remains in `triage_service.py`.

Severity classification is deterministic. Recommendation generation uses the pluggable provider interface:

- `DeterministicTriageProvider`
- `OllamaTriageProvider`

The deterministic provider is the default and safe fallback.

## Data Model Overview

Core tables:

- `users`: registered users and roles
- `incidents`: submitted incidents
- `triage_results`: generated triage output and approval state
- `triage_jobs`: async Celery job tracking
- `runbooks`: operational runbook metadata
- `runbook_chunks`: searchable runbook chunks and embeddings
- `audit_logs`: state-changing action history

Runbook chunks store local embeddings using pgvector in PostgreSQL. Tests use SQLite-compatible fallback behavior.

## Human Approval

Triage output can be generated by deterministic rules or a local LLM. Even validated output may be incomplete, stale, or wrong. Human approval keeps generated recommendations advisory until an engineer reviews them.

Approval state is stored on `triage_results`:

- `pending`
- `approved`
- `rejected`

Approval and rejection actions are audit logged.
